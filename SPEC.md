# TileLayout — спецификация MVP

Рабочий документ для реализации. Долгосрочное видение продукта — в [tech_spec.md](tech_spec.md);
там, где документы расходятся, действует этот.

---

## 1. Что делает MVP

Пользователь задаёт прямоугольную комнату, дверь, несколько объектов на полу, формат плитки
и ширину шва. Система выдаёт до 12 **именованных** вариантов раскладки пола, каждый —
с SVG-планом, таблицей объективных метрик и текстовым объяснением. Пользователь переключает
режим оптимизации и видит, как меняется порядок вариантов и что отсеялось. Результат
шарится ссылкой.

**Только пол.** Стены, потолок, короба — вне MVP.

---

## 2. Ключевые архитектурные решения

| Решение | Обоснование |
|---|---|
| Генерация — фиксированный набор именованных стратегий, а не перебор «сотен» вариантов | Пространство решений для прямоугольника — два непрерывных параметра `(ox, oy)`. «Сотни» дают визуально неразличимый шум. Осмысленных кандидатов — единицы, и у каждого есть человеческое название. |
| Ранжирование — вектор метрик + правила режима. Единого взвешенного `score` нет | Веса неоткуда взять: датасета экспертных оценок не существует. Подобранные на глаз коэффициенты делают продукт нефальсифицируемым. Жёсткие отсечки в мм объяснимы пользователю дословно. |
| Без backend и без БД | Расчёт — чистая функция от ~30 чисел, единицы миллисекунд в браузере. БД обслуживает аккаунты, которых в MVP нет. Состояние — `localStorage` + URL. |
| Без OpenAI | Объяснение варианта — пересказ уже посчитанных чисел; шаблонизатор делает это мгновенно, детерминированно и не переврёт число рядом с чертежом. LLM — необязательный слой позже. |
| Все размеры — целые миллиметры (`int`) | Float даёт накопление ошибки и сравнения вида `49.9997 < 50`. |
| Один этап визуализации (SVG), а не два | «Схематичный 2D план» и «SVG-визуализация» из ТЗ — одно и то же; промежуточный рендер пришлось бы выбросить. |

## 3. Модель данных

Все линейные величины — целые миллиметры. Начало координат — левый нижний угол комнаты,
ось X — вправо, ось Y — вверх (математическая ориентация; SVG инвертирует Y при рендере).

```ts
type Mm = number; // целое

interface Room {
  width: Mm;   // по X
  height: Mm;  // по Y
}

interface Tile {
  width: Mm;
  height: Mm;
  grout: Mm;   // ширина шва между плитками
}

type ObjectKind =
  | 'bath' | 'cabinet' | 'installation' | 'washer'   // класс covers
  | 'toilet' | 'sink' | 'shower'                     // класс stands
  | 'door';                                          // класс opening

interface RoomObject {
  id: string;
  kind: ObjectKind;
  x: Mm; y: Mm; w: Mm; h: Mm;   // AABB на плане
  focal?: boolean;               // участвует в focalOffset
}

interface Project {
  room: Room;
  tile: Tile;
  objects: RoomObject[];
  wallGap: Mm;    // периметральный зазор, по умолчанию 0
  mode: ModeId;
}
```

**Классы объектов** (выводятся из `kind`):

- `covers` — закрывает пол (ванна, тумба, инсталляция, стиральная машина). Подрезки под ним
  не видны и не штрафуются.
- `stands` — стоит на полу, пол вокруг виден (унитаз, раковина-тюльпан, душевая зона).
  В видимость входит полностью.
- `opening` — дверь. Задаёт точку обзора.

Плитка считается скрытой, если укрытие закрывает **не менее 90 %** её площади. Порог высокий
намеренно: ошибочно счесть подрезку скрытой хуже, чем перестраховаться. Как следствие, ванна
короче стены не прячет подрезки выше себя — и это правильно, они действительно видны.

**Подвесная мебель прячет не весь свой габарит.** У предмета задаётся высота нижней кромки
`bottomHeight`; при `0` он стоит на полу и закрывает всё под собой. Иначе луч зрения от глаза
на высоте `EYE_HEIGHT = 1600` мм проходит под кромкой и падает на пол на расстоянии
`L·h / (E − h)` за ней, где `L` — расстояние от наблюдателя до передней грани. Всё, что
дальше этой точки, скрыто корпусом; ближе — просматривается.

Пример: подвесная тумба глубиной 500 мм с кромкой на 250 мм, передняя грань в 1200 мм от
двери. Видно `1200·250/1350 ≈ 222` мм пола под ней, скрыты остальные 278 мм у стены.
Подсветка по нижней кромке геометрию не меняет — она освещает ровно ту полосу, которая и так
на виду, поэтому прятать подрезку туда нельзя.

Отсюда следствие: **что именно скрыто, зависит от того, откуда смотрят.** Без заданной двери
подвесная мебель не прячет ничего — консервативно и безопасно.

`wallGap = 0` по умолчанию: компенсационный зазор у стены физически существует, но скрыт
плинтусом или герметиком, и плиточники считают подрезку до стены.

## 4. Вариант раскладки

Вариант полностью описывается четырьмя числами:

```ts
interface Layout {
  ox: Mm;                        // смещение сетки по X, 0 <= ox < stepX
  oy: Mm;                        // смещение сетки по Y, 0 <= oy < stepY
  orientation: 0 | 90;           // поворот плитки
  rowShift: 0 | 1/3 | 1/2;       // смещение соседних рядов
}
```

Соглашение: **ряды идут полосами вдоль оси X**, высота ряда — `tile.height + grout`
(после применения `orientation`). `rowShift` сдвигает каждый следующий ряд по X на
`rowShift * stepX`. «Направление укладки вдоль/поперёк помещения» из ТЗ — это `orientation`.

```
stepX = effTileW + grout
stepY = effTileH + grout
где (effTileW, effTileH) = orientation === 0 ? (w, h) : (h, w)
```

## 5. Стратегии генерации

`ox` и `oy` выбираются независимыми одномерными стратегиями; итоговые варианты —
декартово произведение с последующей дедупликацией.

| Стратегия | Смысл | Название для пользователя |
|---|---|---|
| `centerTileEntry` | целая плитка по **оси двери** | «Плитка по оси входа» |
| `centerJointEntry` | шов по **оси двери** | «Шов по оси входа» |
| `centerTile` | целая плитка по центру оси | «Плитка по центру» |
| `centerJoint` | шов по центру оси | «Шов по центру» |
| `fromEntry` | целая плитка от наружной кромки проёма | «Целая от проёма» |
| `flushStart` | целая плитка от стены 0, вся подрезка в конец | «Целая от стены» |
| `flushEnd` | зеркально `flushStart` | «Целая от дальней стены» |
| `alignObject` | линия шва совмещается с гранью `covers`-объекта | «Шов по краю: ванна» |
| `alignFocal` | линия шва совмещается с осью фокального объекта | «По оси раковины/ванны» |

`centerTile` и `centerJoint` обе дают равные подрезки по краям, но отличаются на полшага —
одна почти всегда даёт крупную подрезку, другая мелкую. Обе нужны.

`fromEntry`, `alignObject`, `alignFocal` применимы только при наличии соответствующих
объектов; иначе не генерируются.

`centerTileEntry` / `centerJointEntry` выравнивают сетку по оси дверного проёма, а не по
оси комнаты. Когда дверь смещена от центра стены, это разные раскладки, и практика
показывает, что выигрыш крупный: на реальном санузле 2600×1700 с проёмом, смещённым на
210 мм, выравнивание по оси входа подняло минимальную видимую подрезку со 192 до 548 мм
при сохранении симметрии. Генерируются только при заданной двери, по той оси, что поперёк
взгляда.

`fromEntry` привязывает сетку не к стене, а к **наружной кромке проёма**: плитка проходит
порог насквозь и входит в помещение всей оставшейся глубиной. Продольного роспуска у входа
нет вообще — самый просматриваемый кусок режется только по контуру проёма. Предложено
практикующим плиточником на реальном санузле 2600×1700: вместо полосы 247 мм у порога
ложится 450 мм, а ряд, добирающий глубину помещения, уходит с дальней стены под ванну
и тумбу. Плата — весь допуск помещения собирается в этом одном скрытом ряду, поэтому
раскладка чувствительна к фактической глубине: считать её надо по промеру, а не по проекту.
Генерируется только при заданной глубине проёма, по оси, перпендикулярной стене с дверью.

`alignObject` ставит шов ровно на грань мебели: подрезка уходит под ванну целиком, а на
открытом полу линия начинается с целой плитки. Грани, совпадающие со стеной, пропускаются —
это уже `flushStart`/`flushEnd`. Приём неочевиден для пользователя, поэтому лучший такой
вариант показывается всегда, даже если по общему рангу он не попал в список.

**Ограничения на комбинации:**

- `orientation: 90` генерируется только при `tile.width !== tile.height`.
- `rowShift: 1/2` **запрещено при длине плитки ≥ 900 мм** — производители крупноформата
  запрещают перевязку в половину из-за прогиба плиты («пропеллер», перепад на шве).
  Максимум 1/3. Правило жёсткое, с объяснением в UI.

**Дедупликация:** варианты схлопываются по ключу
`(cutLeft, cutRight, cutTop, cutBottom, orientation, rowShift)`. При совпадении сохраняется
вариант с более «объяснимым» названием (порядок приоритета — как в таблице сверху).

**Отсечка:** после ранжирования показывается не более 12 вариантов.

## 6. Метрики

Считаются полным обходом сетки (при `rowShift != 0` подрезки по X различаются от ряда к ряду,
аналитической формулы по осям недостаточно).

| Метрика | Определение | Единица |
|---|---|---|
| `minCut` | минимальная подрезка по всему периметру | мм |
| `minVisibleCut` | то же, исключая зоны под `covers`-объектами | мм |
| `cutTileCount` | число подрезанных плиток | шт |
| `wholeTileCount` | число целых плиток | шт |
| `asymmetryX` | \|cutLeft − cutRight\| | мм |
| `asymmetryY` | \|cutTop − cutBottom\| | мм |
| `entryAsymmetry` | отклонение от симметрии относительно **оси двери** | мм |
| `entryMinCut` | минимальная подрезка внутри зоны обзора | мм |
| `focalOffset` | расстояние от оси фокального объекта до ближайшего шва (минимум по объектам) | мм |
| `wasteArea` | площадь отхода | мм² |

**Зона обзора** — сектор ±45° от центра дверного проёма до противоположной стены.
Полноценный рейкастинг для плоского пола не нужен.

**`entryAsymmetry` считается относительно оси двери, а не оси комнаты.** Человек, стоящий
в дверях, оценивает симметрию относительно собственного взгляда — это расхождение с ТЗ,
где симметрия и вид при входе были независимыми критериями.

Формализация: раскладка симметрична относительно оси взгляда тогда и только тогда, когда
на оси лежит либо шов, либо центр плитки, то есть смещение сетки относительно оси кратно
половине шага. Метрика — расстояние до ближайшего такого положения, в миллиметрах;
диапазон `[0, step/4]`. При перевязке рядов усредняется по встречающимся смещениям, но
только если ряды идут поперёк взгляда — иначе перевязка уходит в глубину и на поперечную
симметрию не влияет. Расхождение до 5 мм на глаз не читается и трактуется как симметрия.

**Вид от входа — не только метрика, но и способ показа плана:** план разворачивается в
систему координат наблюдателя (глубина от порога вверх, право наблюдателя вправо), поэтому
одна и та же комната выглядит по-разному при двери на разных стенах.

`focalOffset` считается «совпадением», если он меньше `grout / 2`.

## 7. Режимы

Режим — это фильтр плюс порядок сортировки. Отсечённые варианты не выбрасываются молча:
UI показывает «отброшено N вариантов: подрезка меньше 30 мм».

```ts
interface Mode {
  id: ModeId;
  reject: (m: Metrics) => string | null;  // причина отсева или null
  sort: Comparator[];                      // лексикографически
}
```

| Режим | Отсечка | Порядок сортировки |
|---|---|---|
| **Designer** | `minVisibleCut < 100` | `entryAsymmetry` ↑, `focalOffset` ↑, `minVisibleCut` ↓ |
| **Economy** | — | `wasteArea` ↑, `cutTileCount` ↑ |
| **Symmetry** | — | `asymmetryX + asymmetryY` ↑, `entryAsymmetry` ↑ |
| **Installer** | `minCut < 30` | `cutTileCount` ↑, `minCut` ↓ |

Пороги 30 мм и 100 мм — отраслевые: подрезка тоньше ~30 мм крошится при резке и почти
не приклеивается; подрезка тоньше ~100 мм в поле зрения читается как ошибка.
Пороги вынести в конфиг, они будут калиброваться (см. §10).

## 8. Объяснение варианта

Детерминированный шаблонизатор поверх метрик. Никаких вызовов модели.

```
«Плитка по центру, смещение 1/3»
✓ при входе раскладка симметрична (отклонение 8 мм)
✓ ось шва совпадает с осью раковины
✓ минимальная видимая подрезка — 280 мм
✗ 14 подрезанных плиток — больше, чем у варианта «Целая от входа»
```

Каждая строка порождается правилом с порогом; сравнительные строки («больше, чем у…») —
из соседних вариантов в текущем ранжировании.

---

## 8а. Дверной проём

Порог **не набирается отдельной вставкой** — узкая полоса по линии стены в самом
просматриваемом месте выглядит как ошибка. Плитка основного пола продолжается в проём
и режется уже по стыку с соседним покрытием.

Поэтому проём — не вырез, а **прирост площади**: прямоугольник `ширина проёма × толщина
перегородки`, лежащий за стеной, снаружи прямоугольника помещения. Та же сетка строится
в нём той же функцией `buildTilesIn`.

Метрики проёма:

| Метрика | Смысл |
|---|---|
| `seamless` | плитка проходит проём насквозь без шва — так и должно быть |
| `outerCut` | размер куска у внешней кромки, где идёт стык с другим покрытием |
| `narrowestPiece` | ширина самого узкого куска в проёме |

---

## 8б. Отсев непрактичных вариантов

Мелкие подрезки убираются жёстким правилом, а не весами:

- `minCut < 30 мм` — такую полоску не отрезать и не приклеить, даже если её не видно;
- `minVisibleCut < 50 мм` — на виду подрезка крошится при резке и плохо держится;
- `minVisibleCut < 100 мм` — на виду читается как ошибка укладки;
- узкий кусок в дверном проёме тоньше 50 мм.

Порог для скрытой подрезки ниже, чем для видимой, намеренно: под ванну и тумбу
сознательно уводят ряд, добирающий погрешность помещения, и скол там ничего не стоит.
Ранее правило 50 мм применялось ко всем подрезкам без разбора и отбрасывало `fromEntry`,
хотя его тонкий ряд не виден ниоткуда.

Отсев не молчаливый: интерфейс показывает, сколько вариантов ушло и по какой причине.
Если правило отбросило бы всё, оно пропускается — показать плохой вариант честнее, чем
не показать никакого.

## 9. Расчёт материала

Считается и показывается всегда, отдельным блоком: целых плиток, подрезанных, площадь пола,
площадь отхода, рекомендуемая закупка с запасом (по умолчанию +10%, настраивается).

Расхождение с ТЗ намеренное: ТЗ отказывается от расчёта количества ради позиционирования.
Позиционирование верное, но число выпадает из раскладки бесплатно, и без него пользователь
уходит в обычный калькулятор.

## 10. Калибровка (обязательный этап, до полировки UI)

Собрать 10–15 реальных планировок санузлов, прогнать через движок, показать результаты
2–3 практикующим плиточникам и дизайнеру с вопросом «какой вариант выбрали бы вы».

**Метрика качества:** попадание их выбора в топ-1 и топ-3.

Если совпадения нет — чинятся правила и пороги, а не интерфейс. Без этого этапа
ранжирование остаётся вкусовщиной, которую нечем защитить.

**Первая точка сверки уже есть.** Плиточник, смотревший санузел из `DEFAULTS`, выбрал
раскладку `fromEntry`, которой движок тогда не умел строить, и не возражал против скрытой
полосы 44 мм. Отсюда две правки: сама стратегия (§5) и разделение порога подрезки на
видимый и скрытый (§8б). Числа 30 / 50 / 100 по-прежнему не откалиброваны — известно
только, что 44 мм под мебелью практика допускает.

## 12. Ограничения MVP (показывать пользователю)

**Комната считается идеальным прямоугольником.** В реальности стены не параллельны, углы
не равны 90°, расхождение 10–30 мм на 3 метра — норма, и опытный плиточник компенсирует
именно это выбором старта. Предупреждение обязательно, иначе на объекте раскладка сойдётся
иначе, чем на экране.

**Вне MVP:** стены и потолок; помещения сложной формы, ниши, выступы, короба; диагональ,
ёлочка, палубная раскладка; 3D и фотореализм; распознавание планов БТИ и фото; несколько
форматов плитки в одной раскладке; декоры и бордюры; уклоны в душевой; тёплый пол.

## 13. Критерий готовности

Пользователь вводит прямоугольную комнату, дверь, 1–3 объекта, формат плитки и шов →
получает ≤12 именованных вариантов с SVG-планом, метриками и объяснением → переключает
режим и видит изменение порядка и причины отсева → делится ссылкой.
